В исследованном ZIP присутствуют:

- создание/открытие/сохранение `.cfgproj` в `MainWindow/MainWindow.LocalProject.cs`, `Infrastructure/Projects/ProjectPackageService.cs`;

Это **опорные компоненты**, не свидетельство уже готового полноценного Compare/Sync. Проверь фактические вызовы, пользовательский маршрут и тестовое покрытие.

## 2. Концепция

- **Online**: живая SQL Server БД, её содержимое может изменяться независимо от Configurator.
- **Offline**: переносимая, редактируемая локальная копия (`.cfgproj`). Её действия не должны скрыто писать в SQL Server.
- **Baseline**: неизменяемый снимок исходного состояния, привязанный к моменту создания/обновления Offline-проекта. Не перезаписывать его при обычном сохранении правок.
- **Compare**: сопоставление **таблиц → строк → значений ячеек** и показ конфликтов с учётом Baseline.
- **Минимальная единица переноса — строка**; различия показываются до ячейки. При `UPDATE` обновляются только согласованные изменённые поля, без слепой перезаписи соседних значений.

## 3. Обязательный функционал

### 3.1. Корректность Online/Offline

- Проверить создание копии, открытие, сохранение, восстановление после перезапуска, переключение источников и отсутствие скрытых SQL-вызовов при работе Offline.
- Поддерживать неизвестные заранее схемы таблиц и множество проектов; не зашивать `dbo.Valves`, `Record`, `PLC` как универсальные ключи.
- После работы в Offline обычное сохранение `.cfgproj` не должно менять Baseline. Отдельное подтверждённое обновление снимка — другое действие.
- Пакет проекта и миграции формата должны сохранять обратную совместимость с существующими файлами; неизвестные/неподдержанные данные нельзя тихо терять.

### 3.2. Compare: дерево различий

- Доступная из общей рабочей области команда **«Сравнить Online ↔ Offline»**; Compare не становится пятым функциональным режимом.
- Показывать дерево/список таблиц со счётчиками: совпадают, только Online, только Offline, различаются, есть конфликт, нельзя сопоставить.
- При выборе таблицы показывать строки с понятным статусом: одинаковая / добавленная / удалённая / изменённая / конфликтная / неоднозначная.
- При выборе изменённой строки отображать значения **Baseline | Online | Offline** и подсвечивать изменившиеся поля.
- Сравнение структуры таблицы (поля/типы/nullable и пр.) отделить от сравнения содержимого. **Автоматическая синхронизация DDL в этом этапе запрещена.**
- Направления переноса пометить явно: `Online → Offline` и `Offline → Online`, отдельные стрелки, читаемые подписи и сводка операции. Двусмысленные стрелки недопустимы.
- Для отсутствующего подключения, пустого проекта, крупных таблиц, ошибок загрузки и отмены операции отображать корректные состояния; избегать полной блокировки UI при больших объёмах.

### 3.3. Идентификация и трёхстороннее сравнение

- Использовать реальные SQL PK/UNIQUE или существующие **проверенные** сопоставления `ProjectMapping.KeyColumns`. Не выводить идентичность строки только из порядка строк, индекса UI или имени, которое может повторяться.
- Для отсутствующих/неуникальных ключей показывать проблему и **блокировать автоматический перенос** таких строк. Ручная настройка логических ключей будет расширена в этапе 03.
- Определять: изменился Offline относительно Baseline; изменился Online относительно Baseline; обе стороны изменили одно и то же поле по-разному; запись удалена/появилась; коллизия ключа.
- Если обе стороны изменили независимые поля, показывать это явно; не объединять их автоматически без подтверждённого и проверяемого правила.
- Сравнение значений делать типобезопасно: `NULL` vs пустая строка, числа, даты, бинарные данные, регистр/коллация по правилам схемы. Не опираться на `ToString()` как универсальный алгоритм сравнения.

### 3.4. План переноса и применение

- Пользователь выбирает **строки** и направление. Сначала формируется `Preview` с типами операций `INSERT / UPDATE / DELETE`, источником, целью, количеством затронутых строк, конфликтами, заблокированными элементами.
- Полный перенос таблицы — только как явное выделение всех её строк и с показом количества; **никакой скрытой замены всей таблицы**.
- Переиспользовать `SyncPlan` и его fingerprint, подтверждение пользователя и лимит количества операций, где применимо.
- Реализовать защищённое **Online → Offline** на локальном проекте с проверкой выбранных строк и обновлением отображения. Учитывать несохранённые изменения локального проекта: конфликт нельзя молча затереть.
- Направление **Offline → Online** на этом этапе должно показывать полный Preview, проверки и причины блокировок, но **не должно включать фактическую запись в Online**. Не обходить `SyncSafetyPolicy.AllowOnlineWrites = false` и не добавлять скрытый обходной SQL-вызов. Финальное разрешение Online Apply — после этапа 03.
- Перед любым применением проверять, что проект/цель/выбранные записи и версии соответствуют плану; изменившийся план или исходные данные требуют нового Preview.
- Обновлять Baseline **только для успешно синхронизированных строк и только по явным правилам**, не сбрасывая несвязанные локальные изменения. Документировать политику обновления Baseline и покрыть тестами.
- В журнале фиксировать намерение, направление, время, пользователя, статус и идентификаторы операций, но не пароли и секреты.

## 4. Безопасность: обязательные ограничения

- Никаких испытаний изменения данных на сервере предприятия. Используй mock/in-memory, тестовую локальную базу или изолированный SQL стенд с явно разрешённой записью.
- Preview или нажатие «Сравнить» **никогда не выполняет запись**.
- При конфликте, неизвестном идентификаторе, недоступной схеме или невалидной зависимости — **fail closed**: блокировать применение соответствующей операции, а не угадывать.
- Не использовать прямые SQL-строки из данных пользователя как идентификаторы таблиц и полей; параметры для значений, allowlist/проверенная схема для идентификаторов.
- Не создавать/изменять SQL PK/FK, не мигрировать схему, не подключать Siemens.

## 4.1. Обязательные испытания на изолированных SQL-копиях — раунд А

Цель: выяснить, **что Compare реально распознаёт**, как ведёт себя при утраченных/ошибочных связях и какие ошибки возникают **до** внедрения подтверждённой логической карты этапа 03. Не объявляй успешное сравнение доказательством целостности базы.

**Подготовка стенда:**

1. Используй только отдельный экземпляр SQL Server / изолированную БД, восстановленную из тестового бэкапа; предпочтительно с обезличенными данными. Проверить возможность восстановления копии и зафиксировать исходное состояние. **Никаких SQL-операций на промышленном сервере**, включая намеренные повреждения данных.
2. До запуска подтвердить целевой сервер, БД, текущие права, отсутствие производственных учётных данных и сетевого доступа к production из тестового процесса по возможности. Одного слова `test` в названии БД недостаточно. Без достоверной изоляции пропустить SQL-интеграционные проверки, зафиксировать блокер, выполнить mock/in-memory тесты.
3. Подготовить воспроизводимые fixtures/скрипты наполнения **только тестовой БД**: обычная схема и специальные копии/состояния с дефектами. Не добавлять в проект реальные логины, пароли или production connection strings; не запускать разрушительные скрипты на произвольном подключении.
4. В **этапе 02** допускается изменять тестовую SQL-копию средствами подготовки fixtures (для моделирования конкурентных изменений), но **сам Configurator не должен выполнять `Offline → Online Apply` даже на тестовой БД**. SQL в этом этапе для Configurator — источник чтения.

**Матрица негативных сценариев** (автотесты по возможности; иначе воспроизводимый ручной прогон):

| Сценарий на тестовой копии | Ожидаемая реакция этапа 02 |
|---|---|
| Физический FK удалён; логическая ссылка существует только в значениях | Не выдумывать подтверждённую связь. Compare показывает то, что может установить, и не обещает целостность; риск/ограничение документируется для этапа 03. |
| Есть осиротевшая ссылка (`Valves.Type` указывает на отсутствующий тип) | Не падать; если не хватает метаданных для достоверного вывода — показывать статус `не проверено` / ограничение, а не `всё корректно`. |
| PK отсутствует, `Record` дублируется, составной ключ не уникален | Строки помечены как неоднозначные; автоматическое сопоставление и перенос этих строк запрещены. |
| Таблица/поле отсутствует на одной стороне; тип/nullable изменились | Показать отличие схемы отдельно; не пытаться синхронизировать DDL или интерпретировать несовместимые данные как равные. |
| Один объект изменён Online и Offline после Baseline; Preview устарел | Обнаружить конфликт/неактуальность; блокировать применение до нового сравнения и подтверждения. |
| Тестовая БД потеряла соединение, чтение завершилось timeout, отказано в `SELECT` | Контролируемая ошибка, безопасное завершение операции, доступный повтор после восстановления; **не** показывать пустую таблицу как подтверждённое совпадение. |
| Повреждён/неполон локальный пакет, некорректное значение или `NULL` | Понятная диагностика, отсутствие молчаливой потери данных и незаметного сброса Baseline. |

**Поведение при ошибках:** перехватывать ожидаемые ошибки SQL/IO/валидации в границах UI-операции, не допускать необработанного падения окна или процесса; показывать короткую причину и затронутый объект, а в диагностическом журнале — тип сбоя и технические сведения **без секретов**. `Ошибка чтения`, `совпадает` и `связей не найдено` — разные состояния. Не делать бесконечных автоповторов, не скрывать частичный результат как полный.

**Зафиксировать итог раунда А:** для каждого сценария — подготовленное состояние, ожидание, фактический статус/сообщение/исключение, прошёл/не прошёл, ссылка на тест либо краткие шаги воспроизведения, дефект/ограничение и необходимость подтверждённой карты связей. Сохранить fixtures и регрессионные тесты для повторного раунда Б на этапе 03. Нельзя утверждать, что **неизвестные программе** отношения обнаружены автоматически.

## 5. Критерии приёмки

- [ ] Offline-проект корректно создаётся, редактируется, сохраняется и переоткрывается без SQL-записи.
- [ ] Baseline позволяет обнаружить независимые изменения Online/Offline и конфликт.
- [ ] Compare показывает таблицы, строки и конкретные поля, плюс различия схемы отдельно.
- [ ] Сопоставление по неуникальному/неизвестному ключу не проходит автоматически.
- [ ] Выборочный `Online → Offline` работает и не затирает невыбранные записи.
- [ ] `Offline → Online` корректно строит Preview, но реальные Online-записи **по умолчанию заблокированы** до этапа 03.
- [ ] Не допускаются незаметная потеря несохранённых данных, молчаливое обновление Baseline, применение устаревшего плана.
- [ ] UI показывает направление, объём, риски и результат операции.
- [ ] Тесты покрывают добавление/изменение/удаление, конфликты и отказ в опасных сценариях.
- [ ] Выполнен раунд А на **доказанно изолированных** SQL-копиях либо честно зафиксирован блокер стенда; тестовые fixtures воспроизводимы.
- [ ] Пропущенные FK, сломанные ссылки, неоднозначные ключи и расхождения схемы не приводят к ложному статусу «безопасно/совпадает».
- [ ] Ошибки SQL-доступа, таймауты и повреждённый Offline-пакет обработаны без аварийного завершения и без потери данных.
