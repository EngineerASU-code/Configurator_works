# Промпт для исправления Configurator 6.0.1

Ты разрабатываешь Windows-приложение Configurator в `D:\AI_lobby\GASS_Configurator`. Приведи реализацию в соответствие с `D:\AI_lobby\Configurator_6.0.1_Architecture_Requirements_and_Rules.docx`. Исправляй код, а не только документацию. Сначала закрой целостность данных, авторизацию и аудит; затем устраняй архитектурное дублирование. Не расширяй функциональность FB и не включай синхронизацию до выполнения этих условий.

Ниже — результаты статического сопоставления ТЗ с текущими исходниками от 12.11.2026. Подтверждённые дефекты отделены от рисков, требующих динамической проверки. Номера строк относятся к текущей копии файлов; все пути ниже — относительно каталога приложения. Эксплуатация уязвимостей, сборка и тестовый прогон в рамках сопоставления не выполнялись.

## Обязательные исправления

### 1. P1 — защитить Offline CRUD от повреждения данных

**Факт:** `Core/Projects/OfflineProjectDataSource.cs:159–173`, `UpdateRecordAsync` находит первую совпавшую запись, изменяет переданные поля и пересчитывает ключ. Перед изменением не проверяет коллизию нового ключа, принадлежность полей схеме, readonly/computed и типовые ограничения. При создании часть проверок ключа есть, но единой схемной валидации CRUD нет. Это расходится с §5.1, §5.5 и требованиями CRUD integrity.

**Сценарий:** создать строки `Id=1` и `Id=2`, изменить первую на `Id=2`. Адаптер допускает дубликат; дальнейшие поиск и удаление становятся неоднозначными. Это дефект прямого API независимо от ограничений окна редактирования.

**Сделай:** общую валидацию команды по схеме, ключам и зависимостям; подготовку результата в рабочей копии; единый commit после всех проверок. Не принимай произвольный список ключевых колонок вызывающей стороны вместо проверенной схемы. Неизвестные поля и неоднозначную идентификацию отклоняй. Для неизвестных серверных ограничений сообщай о невозможности локально подтвердить операцию, не имитируй успешную проверку.

**Приёмка:** изменение ключа на занятый, недопустимые значения, изменение computed/readonly и отказ в середине команды оставляют данные, ключи и индексы неизменными. Одинаковые бизнес-проверки используются обоими адаптерами.

### 2. P1 — заменить неоднозначное кодирование ключей

**Факт:** `OfflineProjectDataSource.cs:192–203`: ключ — соединение `имя=значение` через `|`, без экранирования и тегов типов; `KeyMatches` приравнивает null к пустой строке. Нарушены §5.5 и R-11.

**Сценарий коллизии:** для колонок `A,B` пары `A="x|B=y", B="z"` и `A="x", B="y|B=z"` дают одинаковое представление `A=x|B=y|B=z`.

**Сделай:** единый типизированный `KeyCodec` с различением null/пустой строки, канонизацией чисел/дат и однозначным кодированием составных значений. Примени его к снимкам, CRUD, журналу и восстановлению. Предусмотри миграцию существующих `.cfgproj`, baseline и ссылок журнала без потери идентичности.

**Приёмка:** round-trip и коллизии для разделителей, null, пустых строк, разных типов и культур; после миграции работают сохранение, повторное открытие и восстановление.

### 3. P1 — исключить потерю конкурентных Online-изменений и запись без стабильного ключа

**Факт:** `Services/DatabaseService.Rows.cs:50–92` обновляет строку по ключевым значениям без expected rowversion/before-state. Контракт `IProjectCrudDataSource` не передаёт ожидаемую версию. При этом `TableViewModel.cs:18,69–80,324–337` допускает редактирование таблиц без PK через `UsesValueIdentity`; `DatabaseService.Rows.cs:173` выполняет `UPDATE TOP (1)` по значениям. При совпадающих строках выбор экземпляра неоднозначен. Нарушены §5.3, §5.5 и запреты §8.

**Сделай:** optimistic concurrency для UPDATE/DELETE: expected rowversion либо документированное сравнение исходного состояния; несовпадение — типизированный конфликт с откатом. Введи проверенную стратегию стабильной идентичности. Если её нет, разрешай чтение и отклоняй изменение/удаление; не выбирай произвольную строку через TOP (1). Верни фактические identity/computed/rowversion после записи для последующего аудита.

**Приёмка:** два клиента редактируют одну строку — второй получает конфликт; удалённая или изменённая после чтения строка не перезаписывается; две одинаковые строки без ключа не допускают произвольной модификации.

### 4. P1 — перенести авторизацию в точку выполнения команды

**Факт:** `ProjectWorkspace.cs:121–142,184` проверяет доступность записи, но не полномочия; `OnlineProjectCrudDataSource` также не проверяет сессию. В `MainWindow/MainWindow.Crud.cs` права проверяются в начале обработчика, затем выполняются await/диалог и запись без повторной проверки перед commit. Отдельно `Services/PermissionPolicy.cs:40` предоставляет невизуальные разрешения включённому объекту пользователя с `UserName=admin` до проверки наличия роли. Это слабее `UserAuthorizationService.HasValidAdministrativeSession`, проверяющего принадлежность текущей учётной записи хранилищу. Нарушены §5.6 и R-08.

**Сделай:** единые Application-команды с deny-by-default и проверкой действующей сессии, прав, ProjectId и ревизии workspace при начале и перед commit. Административное исключение свяжи с проверенной сессией; не доверяй одному имени. Сохрани документированный сценарий Offline-доступа без Online-входа через явную локальную политику полномочий.

**Приёмка:** прямой вызов Application API без прав отклоняется; отзыв роли/выход после открытия редактора блокирует запись; искусственный объект `admin` и отсутствие роли не дают привилегий. Отдельно проверь существующие тесты совместимости прав. Это дефект границы авторизации; внешний способ подмены сессии пока не доказан.

### 5. P1 — обеспечить согласованность данных и аудита

**Факт:** `MainWindow/MainWindow.ActionLog.cs:288–312` пишет журнал после изменения данных. При отказе показывает «Данные уже изменены», предлагает ручное сохранение сведений; гарантированной очереди в этом пути нет. Предупреждение уже существует, поэтому не описывай проблему как полностью скрытую ошибку. Нарушены §5.7 и R-05.

**Сделай:** единый ChangeSet с идентификатором операции, actor, project/source, before/after и состоянием. Рабочие базы разных проектов нельзя изменять: не добавляй в них таблицы, связи и другие объекты. Для Online используй устойчивый локальный протокол журнала намерений с восстановлением после аварии и сверкой фактического состояния. Для Offline сохраняй изменения и журнал согласованно внутри пакета. Покрой составные операции режимов 1–3; не ограничивайся одиночными строками. Restore выполняй целиком при совпадении ожидаемого состояния.

**Приёмка:** инъекция отказа журнала/диска/процесса между этапами не оставляет необъяснимого изменения без восстанавливаемого аудита; повтор доставки идемпотентен; конфликт одной части Restore отменяет всю операцию.

### 6. P1 — завершить общий Application/Workspace-путь и жизненный цикл

**Факт:** `MainWindow/MainWindow.Crud.cs:388,462,563` содержит отдельные Offline-ветки; Online использует `TableViewModel/DatabaseService`, а Offline — обработчики `MainWindow.LocalProject.cs`. `Core/Projects/ProjectDataSourceContext.cs:30–31` напрямую создаёт Infrastructure-реализации. Это расходится с §2.1 и §5.1: общий контракт есть, но единая бизнес-логика не завершена.

**Риск:** `SqlProviderGuard.cs:19–26` хранит глобальный Offline-флаг; `ProjectDataSourceContext.Clear/Dispose` может снять его независимо от другого контекста. `SetOfflineActive` синхронно ждёт gate, удерживаемый на время `OpenAsync`; длительность блокировки UI при переключении требует измерения. Пользовательская гонка и запись в чужой проект пока не доказаны.

**Сделай:** поэтапно перенеси CRUD, lookup, проверки и зависимости в общие сценарии; композицию адаптеров вынеси из Core. Закрепи одного владельца активного workspace либо введи scoped capability. Свяжи команды и callbacks с ProjectId/поколением; отменяй устаревшие операции и не допускай применения результатов к новому проекту. Переключение не должно блокировать UI на синхронном ожидании SQL-open.

**Приёмка:** матрица операций режимов 1–3 × Online/Offline; общие контрактные тесты; гонки открытия, запроса, переключения, закрытия и смены проекта. Уже начатый запрос на открытом соединении может завершиться согласно §5.4; новые SQL-операции после перехода запрещены.

### 7. P2 — ограничить доступ к SQL-объектам и проверить доверие подключению

**Факт:** `OnlineProjectCrudDataSource.cs`, `CreateRecordsAsync` экранирует имена и параметризует значения, но не сверяет таблицы/колонки с разрешённой схемой проекта. Экранирование защищает синтаксис, но не определяет полномочия на объект. Подтверждённой SQL-инъекции в этом месте не установлено. `Models/ConnectionSettings.cs:41` безусловно задаёт `TrustServerCertificate=true`: проверка доверия сертификату сервера отключена.

**Сделай:** общую schema/identifier allowlist и типизированные SQL-параметры. Отдельно сохрани явно авторизованный SQL-редактор с его политикой. Для подключения введи безопасную проверку сертификата по умолчанию; исключение для доверенной локальной среды сделай явной настройкой с понятным статусом. Не меняй рабочие подключения молча.

**Приёмка:** обращение к объекту вне выбранной схемы/полномочий отвергается до SQL; вредоносные имена не меняют смысл запроса; интеграционные тесты подтверждают TLS-настройки. Риск перехвата зависит от среды, он не проверялся.

## Текущий статус реализации — 12.11.2026

Архитектурное ограничение проекта: приложение должно адаптироваться к разным существующим схемам БД и их связям. Не изменять рабочие БД; не добавлять в них таблицы, связи или иные объекты. Разрешённая стратегия Online-аудита — только локальный устойчивый журнал намерений и восстановление/сверка. Не считать одинаковую схему БД обязательным условием подключения.

### Реализовано в текущей рабочей копии

- Offline CRUD адаптер сверяет поля и ключи с сохранённой схемой, проверяет доступные типовые ограничения и готовит UPDATE в копии записи до фиксации. Коллизия нового ключа и неоднозначное совпадение отклоняются.
- Добавлен версионированный типизированный кодек ключей с раздельным представлением null/пустого значения, типов и составных ключей; он используется при создании/изменении Offline ключей, чтении Online-снимка и формировании ключей в журнале.
- Online-таблицы без стабильного ключа стали недоступны для изменения через `TableViewModel`. Редактирование по исходным значениям проверяет уникальность совпадения и не выбирает произвольную строку через `TOP (1)`.
- Проверка привилегий больше не выдаёт права только по имени `admin`; административное исключение требует активной проверенной сессии.
- Добавлены тесты на Offline коллизии, readonly/неизвестные поля и кодирование ключей. CI дополнен Debug-сборкой и запуском Debug-тестов.
