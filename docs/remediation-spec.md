# ТЗ на устранение замечаний аудита GASS Configurator

База сравнения — аудит от 24 ноября 2026 г., рабочая копия main на ec1682c с 30 изменёнными и 22 новыми файлами. Цель — безопасная работа нескольких операторов с уже загруженной структурой проекта. Допускаются создание, изменение и удаление экземпляров в существующих таблицах. Структура таблиц, индексы, ограничения, классы и правила архитектуры сохраняются. Ограничение действует для администратора, Online, Offline, Compare, журнала и свободного SQL.

| ID | Требование | Приёмка |
|---|---|---|
| R1 | Оставить просмотр схемы и классов. Закрыть операции изменения структуры и реестра классов в UI и слое записи, включая неявное создание служебных таблиц. Если необязательное хранилище отсутствует, соответствующая функция сообщает об ограничении. | Запросы изменения архитектуры отклоняются до записи. Обычный CRUD работает. Отмена, крестик, ошибка и конкурентное создание не могут удалить таблицу или изменить класс. Снимки схемы до и после совпадают. |
| R2 | Перед удалением проверять ожидаемое содержимое строки и её актуальные зависимости внутри общей транзакции. Конфликт отменяет весь пакет с заменами ссылок. | Два клиента. Изменение неключевого поля, добавление зависимости, изменение зависимой строки и повторное создание проверяются на стенде. При конфликте журнал не обещает успешной операции. |
| R3 | Одна конфигурация аутентификации для проверки сервера и открытия базы. Проверять сертификат сервера. Устаревший ответ перечня БД отбрасывать. | SQL и Windows Authentication проверяются по отдельности. Недоверенный сертификат отклоняется, смена полей во время соединения сбрасывает результат. |
| R4 | Compare перепроверяет исходную Online-запись, отклоняет устаревшие планы, сохраняет допустимые метаданные с контролем конкурентной записи. Перенос архитектуры закрыт. | Изменить источник и назначение между preview и применением. Цель сохраняет свои данные при конфликте. |

| R6 | Библиотека SQL проверяет версию редактируемого запроса. Ожидание подтверждения DML ограничено по времени и завершается откатом при тайм-ауте или закрытии. | Конкурентная запись не перетирается. Проверить с двух соединений, что блокировка снимается. |
| R7 | Обновить уязвимый Pkcs, усилить требования к новым паролям администратора, предусмотреть переход для существующих учётных записей. | NuGet-аудит основных и транзитивных зависимостей. Проверить первоначальную настройку, смену пароля и доступ к существующему профилю. |
| R8 | В редакторе FB при сбое сохранения восстановить исходную коллекцию. Пункт документации должен открывать содержательную справку. В экспорт Record включить базу, класс и номер класса. | Отмена после сбоя записи сохраняет исходные данные. Проверить справку и содержимое XLSX. |

Порядок исполнения — сначала запреты на структурные операции и защита записей, затем подключения, Compare, Offline, зависимости и замечания интерфейса. Итоговая проверка включает Release xUnit, выделенный LocalDB, ручной цикл на EK_Omsk_Juice с временной маркированной записью, контроль её удаления, сравнение схемы и независимое ревью. Выполнение и результаты фиксируются по каждому ID. Положительный тест одной кнопки не закрывает всё требование.

## Детали реализации и исходные доказательства

- R1 закрывает три замечания об удалении класса по крестику, раздельном удалении таблицы и класса и перезаписи номера класса другим клиентом. Раздел «Структура БД» сохраняет просмотр графа и справочников. Проверить прямой CRUD по системным таблицам, вставку из буфера, импорт пакета, перенос строк реестра через Compare, отмену через журнал и доступ через интерактивный SQL. Удаление или изменение записи класса через любой из этих путей должно завершаться до изменения данных. Отдельно проверить DDL в DatabaseService.Templates, ClassRegistryService и SavedSqlQueryStore. Для свободного SQL использовать консервативную проверку целевых объектов и существующие ограничения прав SQL Server. Если цель записи нельзя проверить однозначно, останавливать команду. Назначение серверных прав остаётся отдельной операцией администратора.
- R2 применяется к режимам «БД проекта» и «Объекты проекта», к одиночному и пакетному удалению. Для таблиц без версии строки использовать сравнение ожидаемых значений и проверять число затронутых строк. Если запись невозможно однозначно идентифицировать, показывать причину отказа. Для удаления и повторной вставки абсолютно идентичной строки без неизменяемого идентификатора или версии схема не даёт способа различить экземпляры. Это ограничение следует документировать. Поздняя вставка ссылки другим SQL-клиентом уже после успешного удаления также требует согласованного поведения всех писателей.
- R3 проверяется на сохранённых подключениях предыдущей версии. Переход к проверке TLS должен давать понятное сообщение при недоверенном сертификате. Установку сертификатов и изменение настройки сервера ТЗ не предусматривает.
- R4 для раздельных источников зафиксировать момент перечитывания источника и гарантии атомарности записи назначения. Не обещать общей транзакции для SQL Server и файла. Отдельно проверить конфликт между двумя процессами при сохранении одних и тех же допустимых проектных настроек.
- R7 для Pkcs ориентир в ветке 8.0 — исправленная версия от 8.0.2. Проверять фактически разрешённую версию и доступность базы рекомендаций NuGet. Для паролей проверить граничные значения, отсутствие вывода пароля в журналах и безопасную смену старого пароля без автоматического сброса администратора.
- R9 исходные измерения — 19 из 94 правил с несовпадениями, 124 конфликтных бита, включая 118 с участием нулевого смещения, 100 записей с кодом области «КЛ» без совпадения в справочнике. Для Prog_Statuses установить полный бизнес-ключ. Ни одна из этих цифр сама по себе не определяет правильное новое значение записи. Предметное решение должно указывать таблицу, критерий выбора строк и ожидаемый результат. Массовая перенумерация и автоматическое исправление нулей не входят в работы.

## Доказательства для закрытия

Исходный полный прогон до реализации — 434 из 434 тестов прошли. Это база сравнения. После реализации для каждого R1–R9 приложить результат, команду или протокол, проверенную версию, условия и открытые ограничения. Для R1 сравнить таблицы, столбцы, типы, ключи, индексы, связи и записи реестра классов. Для R2, R4 и R6 приложить результаты двух независимых сессий. Для ручных проверок указать роль, кнопку, ожидаемое и наблюдаемое поведение, для операций записи дополнительно сверить результат независимым SELECT. Отдельно зафиксировать блокировки или непройденные сценарии до решения о выпуске.
