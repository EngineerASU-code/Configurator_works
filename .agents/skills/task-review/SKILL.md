# Проверка выполненной задачи

Проведи независимую проверку текущих изменений. Ищи реальные дефекты, регрессии и нарушения требований, а не стилистические придирки. Выполни один проход без самостоятельной серии повторных ревью или исправлений.

## Контекст и границы

- Возьми исходную задачу и критерии приёмки из текущего контекста. Если их нет, явно отметь ограничение и проверяй доступный код, не придумывая требований.
- Учитывай `AGENTS.md` и применимые инструкции проекта.
- Определи базу сравнения и сообщи, что именно проверяешь: незакоммиченные изменения, диапазон коммитов или изменения относительно базовой ветки. Учитывай индекс, рабочее дерево и новые файлы, если они входят в задачу. Не угадывай базовую ветку. При неочевидной базе укажи ограничение охвата.
- Не меняй файлы, не форматируй код и не создавай коммиты. Исправления требуют отдельного поручения. Не включай генерируемые тестами артефакты в результат изменений.

## Работа

1. Посмотри diff и список изменённых файлов. Не перечитывай весь репозиторий.
2. Сопоставь реализацию с целью и критериями приёмки.
3. Проверь по приоритету:
   - неправильное поведение, нарушенные инварианты и регрессии;
   - крайние случаи, обработку ошибок и отказоустойчивость;
   - потерю или порчу данных, безопасность и работу с секретами;
   - совместимость публичных интерфейсов и форматов данных;
   - отсутствие теста для существенного нового поведения.
4. Читай соседний код только для проверки конкретной гипотезы.
5. Запусти существующие подходящие проверки: сначала быстрые, затем более широкие при необходимости. Долгие или потенциально разрушающие проверки требуют согласования. Не повторяй уже прошедшие проверки без изменений или другой конкретной причины.
6. Отрази ошибки линтера и компилятора в результатах проверок; не дублируй их отдельными ИИ-замечаниями.

Используй адресный контекст и короткие диагностические фрагменты, без полных логов успеха. Если не хватает доступа, зависимостей, среды или требований, останови зависимую часть проверки и зафиксируй ограничение.

## Замечания

Для каждого подтверждённого дефекта укажи:

- Серьёзность: `BLOCKER` / `MAJOR` / `MINOR`.
- Место: файл и строка или диапазон, если доступны.
- Конкретный сценарий и последствия.
- Основание: код, тест, воспроизведение или чёткую логическую цепочку.
- Краткое направление исправления без изменения кода.

Непроверенные подозрения вынеси отдельно в «Требует проверки». Если дефектов не найдено, так и скажи; это не гарантия отсутствия ошибок.

## Отчёт

- **Вердикт:** `PASS` / `FAIL` / `NEEDS VERIFICATION`.
- **Проверено:** база сравнения, затронутые области и важные сценарии.
- **Проверки:** команда → `PASS` / `FAIL` / `NOT RUN`, с причиной при сбое или пропуске.
- **Подтверждённые проблемы:** по убыванию серьёзности либо «не обнаружены».
- **Требует проверки:** только непроверенные риски и пробелы.
- **Итог:** 2–3 предложения с рекомендацией принять изменения или отправить на доработку.

`PASS` допускается, только если не выявлены блокирующие проблемы и достаточные для задачи проверки действительно выполнены. При нехватке данных выбирай `NEEDS VERIFICATION`.
