# Первоначальная настройка проверок качества

Подготовь минимальную, реально работающую систему проверки качества в текущем репозитории с умеренным расходом контекста и токенов. Работай в Codex App, без отдельного Codex CLI и новых внешних сервисов.

## Границы

- Работай только с открытым репозиторием. Не трогай соседние проекты, глобальные настройки и API-ключи.
- Прочитай корневой `AGENTS.md`, если есть, и применимые инструкции во вложенных каталогах. Сохрани существующие правила.
- Установи фактический стек по конфигурации проекта; не предполагай язык или тестовый фреймворк.
- Не меняй прикладной код. Не добавляй зависимости, CI, сторонних агентов, плагины, сервисы или платные интеграции без отдельного запроса.
- Не выполняй опасные или необратимые команды, не удаляй данные и не выводи секреты.
- Проводить исследование репозитория поэтапно: сначала обзор структуры и конфигурации, затем изучение ключевых компонентов и их зависимостей. Не читать все исходники подряд. Исключать генерируемые файлы, бинарники, каталоги сборки и сторонние зависимости. Углубляться только там, где это необходимо для определения архитектуры, команд сборки, тестирования и важных проектных ограничений. Не жертвовать полнотой анализа ради экономии токенов: все ключевые модули должны быть учтены.


## Работа

1. Адресно изучи README, файлы сборки, конфигурацию тестов и существующие скрипты. Не обходи всё дерево без необходимости; исключай зависимости, бинарники, сборочные и сгенерированные файлы.
2. Найди подтверждённые команды сборки, автоматических тестов, существующего статического анализа/линтера и форматирования в режиме проверки без изменения файлов. Укажи рабочие каталоги. Если команды нет, так и сообщи.
3. Запусти наиболее дешёвые и релевантные проверки по одному разу, если доступны среда и зависимости. Для долгих, сетевых, потенциально дорогих или меняющих данные операций сначала сообщи, что требуется; не выполняй их молча. Опасные операции требуют явного поручения.
4. Определи 2–5 наиболее важных рисков будущих изменений и пробелы в тестировании, если они подтверждаются проектом. Не создавай тесты ради процента покрытия.
5. Проверь соответствие `AGENTS.md` проекту. При необходимости внеси только точечные подтверждённые уточнения: команды, критические инварианты, архитектурные ограничения. Сохрани существующие правила, не дублируй их. Если файла нет, создай краткий `AGENTS.md` только с подтверждёнными проектными сведениями.
6. Переиспользуй подходящие команды и скрипты. Не строй инфраструктуру без конкретной необходимости.

Не повторяй успешные проверки без причины. Для ошибок показывай команду и короткий диагностический фрагмент, для успеха — краткий результат. При блокировке останови зависимую работу и зафиксируй причину; не уходи в цикл исправлений.

## Отчёт

Кратко укажи:

1. Стек и структуру, которые удалось установить.
2. Точные команды сборки, тестов, линтера и проверки форматирования с рабочими каталогами.
3. `PASS` / `FAIL` / `NOT RUN` для каждой проверки; причину пропуска или сбоя.
4. Все изменённые файлы либо «нет».
5. Существенные риски и пробелы.
6. Одну приоритетную рекомендацию.

Не называй проверки пройденными, если они не были реально запущены.
